1. What FReSCo actually does, and how we would adapt it

I inspected FReSCo’s NUwU source at the 2024 snapshot f11a55f. One potential represents one particle set. Its constructor makes a Type 1 plan and a Type 2 plan with ntransf = 1. On an energy/gradient call it updates both plans’ points, executes Type 1, builds Fourier coefficients, and executes Type 2 separately for each gradient component.

Type 1: all particlesBuild coefficientsType 2: xType 2: yType 2: z, if 3D

The transform calls are sequential; each can use FINUFFT’s internal thread team. FReSCo also parallelizes some coordinate preparation and gradient-copy loops with OpenMP. It creates compatible plans once and calls setpts again as positions move. It does not use our species task scheduler or our Type 2 cost gate.

Sources: plan creation, energy/gradient implementation, and FINUFFT 2.2 default thread budget. Its default options permit the available OpenMP thread budget; they do not guarantee continuous utilization of every worker.

2. Predicted changes in CPU activity

More workers available within a transform

One species’ spreading, FFT, interpolation, and suitable point-preparation loops can use the internal team. This removes the dependence on having enough species or particle-block tasks to occupy the machine. The requested transform concurrency changes from one internal worker per block to P workers per whole-species call.

Less concurrency between transforms

Species no longer overlap, and contact no longer fills spare transform workers. Each individual transform must scale well enough to replace the concurrency already present in the current schedule. Small calls can spend proportionally more time in coordination.

All force components enter one execution. The current code creates a Type 2 plan with ntransf = dimension, fills a coefficient array for every component, and calls finufft_execute once per particle block. The proposed schedule keeps that batch for the whole species and requests P internal threads. FINUFFT controls how FFT, spreading, and interpolation work is shared across components and workers. A batched API call does not by itself guarantee simultaneous execution of every component.

The default library scheduling should be measured first. FINUFFT provides controls for parallelism across batched transforms versus within a transform; forcing one strategy without measurements could make this small batch slower. Those controls are not changed by this report.

For S species and one current block per species, the current and proposed batched paths both need S Type 1 and S batched Type 2 execute calls when all inverse paths are accepted. Three species therefore need six execute calls in either path, in both 2D and 3D. The optional separate-component variant needs nine calls in 2D or twelve in 3D. This count describes API executions, not the number of underlying FFTs or total arithmetic work.

Bypassing the old one-thread force cost gate is also a real change. It may eliminate direct force loops for eligible species that the gate currently declines, but it may increase transform overhead. A later benchmark must record actual forward and inverse backends for both versions.

Working prediction: more of the available CPUs can participate during a sufficiently large whole-species transform. Full-run utilization will still include serial NLopt and configuration work. At 300 particles per species, the sign and size of the utilization change remain uncertain, and coordination plus separate inverse calls can outweigh gains. A numerical full-run utilization prediction is not supported without phase and scaling measurements.

3. Break-even with batched inverse transforms

For S equal species and P ≥ S workers, assume one current block per species, all inverse paths accepted, and negligible contact/serial work. D is a species’ one-thread density time, F its one-thread batched inverse time, qD and qF the effective internal speedups, and h extra overhead per execute stage.

Current transform span ≈ D + F
Proposed batched span ≈ S × [D / qD + F / qF + 2h]
Optional separate-component span ≈ S × [D / qD + d × G / qF + (1 + d)h]

If qD = qF = q and h = 0, the batched proposal needs q > S to improve this simplified transform span. Three species therefore need more than 3× effective scaling on five workers in this limit. Internal speedups can differ between the batched and separate-component variants; keeping the same slider value when switching is only a hypothetical comparison.

This limiting calculation is not a measured threshold for the complete optimizer. Point setup, contact overlap, unequal species, multiple blocks, and serial work change the balance. G is the one-thread cost of one component in the optional separate-call variant.

4. Explore the tradeoff

Hypothetical model · not fitted to measured timings

The controls describe an imaginary evaluation of the FReSCo-style adaptation. They do not estimate FINUFFT speedup from particle count. Time uses arbitrary units. Both schedules use identical input work; the proposed schedule changes its ordering, internal speedup, and overhead.

Speedup and CPU activity are independent inputs. A transform can use four CPUs on average yet run only twice as fast. Their ratio reflects additional CPU work such as coordination. Average active CPUs is constrained to be at least the selected effective speedup in this model, which assumes threading does not reduce arithmetic work. Threading overhead is an extra elapsed cost per species transform stage.

Exactly what the simulator assumes
  • Equal species, one current Type 1 block and one accepted batched Type 2 block per species. This isolates threading and batching; the effect of bypassing a declined force gate is not numerically modeled.
  • Current schedule: density-plus-batched-inverse chains are assigned to workers, and free workers take contact chunks from a shared queue. Contacts use 4P equal chunks.
  • Proposed default: one whole-species density and one batched inverse execution per species. The optional component mode uses d separate inverse calls instead. Both request the full internal team; all contact work follows the transforms.
  • The order selector changes whether all densities precede the inverses or each species completes in turn. With fixed costs and no cache model, these orders have equal predicted span and CPU work. That is a model assumption, not an equivalence established by measurements.
  • The default batched proposal uses the same one-thread batch cost F as the baseline; the effective speedup and overhead can change. In separate-call mode, G is an independent one-component cost. The model does not silently set d × G = F.
  • Threaded stage duration is D/qD + h for density, F/qF + h for a batched inverse, or G/qF + h for a separate inverse component. CPU time is duration times the specified average active CPUs. Effective scaling here should include corresponding point-preparation/output work; it is not a measured library-only speedup.
  • One serial-duration control aggregates unchanged preparation, reductions, gradient conversion, optimizer work, and I/O. These are drawn together before other work solely to simplify the diagram.
  • Memory contention, per-stage scaling differences within a transform, cache effects, changing optimizer trajectories, and changing force-backend decisions are not separately simulated.

The current-schedule model is not calibrated to the measured 33–34% CLI utilization.

6. Scope and source basis

Only this report and its documentation links are added. The internally threaded adaptation has not been implemented; component batching already exists in the current C++ evaluator. The current cost-model constants were fitted to one-thread FINUFFT tasks; their decisions should not be treated as validated cost predictions for a multithreaded plan.
