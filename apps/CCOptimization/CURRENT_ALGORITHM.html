The cell is fixed in this ground-state call (Switch = 0, pressure = 0). The optimized variables encode particle fractional coordinates. The default algorithm is LBFGS; the CLI also supports other named methods.

Each phase creates a fresh NLOPT_LD_LBFGS optimizer, so its L-BFGS history restarts. The physical coordinates carry forward. These numbers rescale optimizer variables and gradients; they do not resize the physical box or change particle radii.

Stopping and acceptance are separate. maxsteps sets the evaluation limit for each phase (default 10,000). This call supplies −MaxEnergy as NLopt’s stop value; the CLI’s tolerance (default 1e-14) is checked after relaxation. A normal process exit does not establish a ground state.

NLopt uses previous gradients to update its search direction and line search. Its callback reconstructs a configuration, calls SetConfiguration, evaluates energy/forces, and returns the gradient. A line search can request multiple evaluations per accepted optimizer step. The callback also writes periodic configuration snapshots according to its save settings; these are configuration files, not a saved NLopt optimizer history. The requested sample count determines the attempted starts; the run can finish with fewer accepted states. The callback’s C++ preparation and gradient conversion run on the calling thread; the potential opens its own OpenMP teams.

Evidence: optimizer dispatch, phase sequence, NLopt options, acceptance.

2. What an energy/gradient evaluation computes

Collective-coordinate part

ρₛ(k) = Σⱼ∈ₛ exp(i k · rⱼ)
Eₛ = (1 / V) Σₖ vₛ(k) |ρₛ(k)|² + Shiftₛ

Here the sums use the species’ stored constraint list. The displayed quadratic form describes the S(0) = 0 stealthy case with ShiftedCCPotential; other structure-factor targets are outside this formula’s scope.

Each particle belongs to one species. Indexed views give each species its own particle order without copying a separate species configuration. Every configuration update invalidates cached densities.

Contact part

Econtact = Σᵢ<ⱼ max(0, 1 − rᵢⱼ / σᵢⱼ)²
σᵢⱼ = radiusᵢ + radiusⱼ

Pairs include all species and periodic neighbors. The code traverses a cell list, counts each pair’s energy once, and accumulates its force on each endpoint’s traversal. Exactly coincident particles use an explicit deterministic force branch.

Contact cells have width max(rc, (V/N)^(1/d)). This keeps neighbor work local rather than scanning all pairs for every particle.

Etotal = u₀ Σₛ (Nₛ / N) Eₛ + e₀ Econtact
Fᵢ = u₀ (Nₛ / N) Fₛ,ᵢ + Fcontact,ᵢ
gradientᵢⱼ = −Fᵢ · basisⱼ / coordinate_scale

The contact force above already includes e₀. In this CLI ground-state path u₀ defaults to 1; the input contact strength sets e₀.

When NLopt requests a gradient, the callback detects CombinedEnergyForce and calls EnergyAndAllForce. The fused contact walk computes energy and force together. If a callback requests energy alone, it uses Energy() instead.

Evidence: fused callback, gradient conversion, evaluation implementation.

3. How threads are assigned

Schematic · not a timing trace

Switch the backend to see the two schedules implemented in the current code. The diagrams use five requested OpenMP workers. A colored cell means assigned work; it does not imply a measured duration or continuous CPU activity.

Species 1Species 2Species 3ContactCalling thread / shared assemblyHatching = waiting or no assigned work

Direct density: one species uses the team

GetRho_Direct splits wavevectors across ParallelNumThread workers. Each wavevector’s particle sum remains sequential. Species are visited one after another. After their densities are ready, the particle loop computes contact and direct collective forces with the team.

Thus “all threads for species 1 density, then species 2 density, then contact” already resembles the direct path. Contact and direct force evaluation share the final particle loop.

FINUFFT density: tasks share the team

The CLI leaves internal FINUFFT threads at one. Each density particle block is one outer task. Small species can have one block; larger species can have several. Multiple blocks repeat grid/FFT work and are combined in block order.

A single block does not use all five workers internally. Multiple blocks of one species can run on different workers. The diagram assumes one density block and at most one accepted force block per species; it does not predict the actual cost gate.

Dependencies, barriers, and direct fallbacks
  1. PrepareSpecies(true) prepares persistent plans serially, selects eligible species, and applies the joint force cost gate.
  2. Direct or ineligible species fill energy/density before the concurrent region, one species at a time.
  3. RunSpeciesWork dynamically assigns density blocks, followed by the queued multi-block force work. Tasks are ordered by predicted cost; actual worker assignment varies.
  4. The last density worker for a species completes its density reduction and energy, then prepares forces. If exactly one Type 2 block is ready, that same worker executes it immediately. Multiple force blocks are released to waiting workers.
  5. A worker waiting on a force dependency takes contact chunks; if no contact work remains, it yields. Workers with no transform tasks also take contact chunks.
  6. There is no global barrier between all densities and all forces. There is a barrier after species/contact work, followed by a parallel particle loop that assembles total forces. Declined or failed Type 2 work uses direct collective forces in this loop.
  7. Total energy is combined from species and particle slots in fixed index order on the calling thread.

A failed Type 1 block causes that species’ density to fall back to direct sums. Mixed direct/FINUFFT species and multi-block tasks are supported but are not drawn in the simplified example.

Evidence: direct density loop, internal thread default, species preparation, task scheduler, assembly and reduction.

4. Particle motion updates points, while plans can persist

A FINUFFT plan stores reusable transform machinery. It also receives position-dependent state through setpts. Moving particles changes the mathematical transform, so that state must be refreshed before execution.

Plan objectReusable grid / FFT setup
Point stateMatches the current positions
Density cacheValid for current positions

This explorer isolates a density transform’s lifecycle. Production code calls these operations automatically.

RunRhoBlock reads current fractional positions, constructs angles, calls finufft_setpts, then finufft_execute. Type 2 force blocks also call setpts. Plans are created during serial preparation and retained while compatible; changed dimensions, grids, tolerance, thread settings, or block requirements can require plan changes.

Plan reuse does not mean unchanged particle positions or zero position-preparation cost. The same lifecycle works inside an NLopt objective callback. Evidence: current-position update and execution.
