# Four FINUFFT speedups for multi-component CC optimization

## Scope and baseline

The optimization callback constructs a `Configuration`, calls `SetConfiguration()`, evaluates `Energy()`, and then requests `AllForce()` when NLopt needs a gradient (`potential/StructureOptimization.cpp:423–487`). `RelaxStructure_NLOPT()` runs three L-BFGS passes; that schedule stays unchanged (`potential/StructureOptimization.cpp:981–999`). MD also calls the potential through `SetConfiguration()`, `Energy()`, and `AllForce()` (`potential/MD_System.cpp:70–87`).

Production multi runs currently use direct sums: the app makefile has no FINUFFT build or link option (`apps/CCOptimization/makefile:24–45`), and `GetMultiCCO()` constructs the species potentials without selecting a rho backend (`apps/CCOptimization/main.cpp:1152–1164`). The existing optional Type 1 path affects rho only; forces remain direct (`potential/CollectiveCoordinatePotential.h:364–405,467–499`). The prior report retained that division of work and the three-pass optimizer (`docs/finufft/REPORT.md:7–20`).

Timing estimates below are **predictions against the measured 2.8 ms and 9.3 ms direct evaluations**, not benchmark results. They assume five equal species, four outer threads, one FINUFFT thread per call, and default OpenMP waiting. Gains will vary with contact density, mode-grid size, and actual callback count.

## Critique of A–D

**A has the largest uncovered hot spot at high χ**, but its proposed formula needs the implementation’s exact normalization. The code stores only the listed constraints and computes force with a factor \(2/V\) (`potential/CollectiveCoordinatePotential.h:467–483`). Write \(\rho_k=a_k+ib_k\). The direct force is

\[
F_{i,a}=\frac{2}{V}\operatorname{Im}\!\left[\sum_k V_k k_a\overline{\rho_k}e^{ik\cdot r_i}\right].
\]

Thus Type 2 uses **isign=+1**, coefficients \(V_k k_a\overline{\rho_k}\), and the imaginary output; do not add another half-space factor. The multi wrapper then applies \(u_0N_s/N\) (`apps/CCOptimization/MultiStealthyPotential.cpp:401–405`). A force-only transform still needs valid rho first, including when MD calls `AllForce()` without `Energy()`.

**B’s benefit is real but should not be inferred from the 21×21 micro-test alone.** The supplied guru measurements rise from 44 to 190 µs for Type 1 when the grid changes to 41×41. A plan must be rebuilt when grid dimensions or tolerance change, while `setpts` must run for each new position. The existing code recomputes integer modes on every rho call because constraints are public and mutable (`potential/CollectiveCoordinatePotential.h:227–231,261–299`). Cache invalidation needs an explicit contract or a verified fingerprint.

**C cannot safely mean “turn FINUFFT threads up.”** Prior five-component evidence found variable results from internal multithreaded spreading and restored tested repeatability with one internal thread (`docs/finufft/REPORT.md:38–44`). Parallelize *species*, each with its own buffers and plan. The current `Energy()` calls species in order (`apps/CCOptimization/MultiStealthyPotential.cpp:337–342`), and each inner energy creates an OpenMP region (`potential/CollectiveCoordinatePotential.h:441–461`). Set inner parallelism to one while species run concurrently. Simple-interface calls may serialize in planning, so C’s isolated benchmark matters.

**D combines two different changes.** An indexed view is a focused way to remove the species copies made by `UpdateSubconfigs()` (`apps/CCOptimization/MultiStealthyPotential.cpp:301–323`). Fusing contact energy and force is more intrusive: energy visits pairs once in particle-index order, whereas force visits each particle’s neighbors independently and has a special zero-distance rule (`apps/CCOptimization/MultiStealthyPotential.cpp:360–385,421–445`). A shared pair pass would need ordered per-particle force accumulation and careful handling of periodic images. Given the measured 0.15–0.16 ms contact-energy cost, leave that fusion outside the first four branches.

## Final four options, ranked

### 1. Type 2 force transform

Add a FINUFFT force backend to `ShiftedCCPotential::AllForce()` and `Force()`, selected for each multi species. Keep the direct routines callable. Reuse the existing Type 1 eligibility logic for dimensions 1–3, integer reciprocal modes, grid cap, and sparse-grid guard (`potential/CollectiveCoordinatePotential.h:242–300`). Build a zero-filled mode array for each Cartesian component; add coefficients for duplicate mode indices. For standalone A, use `finufft1d2many`, `finufft2d2many`, or `finufft3d2many` with `ntransf=d`, `iflag=+1`, `eps=1e-12`, `modeord=0`, `nthreads=1`. The public 2.5.1 header exposes these interfaces and guru `makeplan/setpts/execute/destroy` (`/home/jaeukk/install/include/finufft_eitherprec.h:55–67,80–85,102–109,132–141`).

Fill global particle results in species index order, apply \(2u_0N_s/(VN)\), and add the existing contact force. A failure at eligibility, allocation, `setpts`, or execution sends the **whole species force** through direct calculation; never retain partially transformed results. Use the current `eps=1e-12` as the starting accuracy setting, then gate acceptance on direct comparisons down to absolute \(10^{-10}\) near zeros. Tightening eps blindly can reject otherwise valid modes under the current rounding budget (`potential/CollectiveCoordinatePotential.h:252–282`). Predicted standalone total: **2.5–2.8 ms at low χ; 6.0–6.9 ms at high χ**.

### 2. Persistent Type 1 plans and mode map

Wrap one guru Type 1 plan per eligible species in RAII storage. Call `finufft_makeplan(type=1, dim=d, n_modes=2K+1, iflag=+1, n_transf=1, tol=1e-12, …)` once for a stable grid; each geometry calls `finufft_setpts(M=N_s, x,y,z, N=0, null targets)` and `finufft_execute(unit_strengths, grid)`. Cache the `modeord=0` mapping, whose first dimension is fastest (`potential/CollectiveCoordinatePotential.h:315–339`). Destroy plans on invalidation and at potential destruction. A-only or direct builds remain available.

Use `finufft_default_opts`, then explicitly set `modeord=0`, `nthreads=1`, `upsampfac=2.0`, and a fixed `spread_sort` choice validated in benchmarking. The installed `finufft_opts` has **no `chkbnds` field**, so do not assign one (`/home/jaeukk/install/include/finufft_opts.h:8–44`). Check finite angles, index and allocation bounds in the wrapper. Preserve the existing direct fallback. Predicted total: **2.0–2.3 ms; 5.9–6.3 ms**.

### 3. Species-concurrent Type 1

After `UpdateSubconfigs()`, compute each species’ rho and CC energy in a fixed-index OpenMP loop with at most `min(S, outer_threads)` workers. Each inner species potential uses one thread, as does FINUFFT. Store `CC_s` in slot `s`; sum slots in ascending species order and then compute contact energy with its existing particle-index reduction (`apps/CCOptimization/MultiStealthyPotential.cpp:360–385`). `AllForce()` must independently ensure rho is ready, as it does today (`apps/CCOptimization/MultiStealthyPotential.cpp:450–463`). Keep fallback local to a species. No shared FINUFFT plan may execute concurrently; B would supply one plan per species.

Use the existing Type 1 options and tolerance. Fixed species and particle orders preserve arithmetic order independent of scheduling. Test 4 and 8 threads, both wait policies, and S=1, 2, 5, 10. Predicted total is **2.2–2.6 ms; 6.0–8.5 ms**, with planning contention the key uncertainty.

### 4. Indexed-view FINUFFT feed

Introduce an optional `ShiftedCCPotential::SetIndexedConfiguration(full_config, species_indices)` binding. Its local particle `j` maps to global `species_indices[j]`; rho, direct force fallback, and Type 1 angle filling all read through that mapping. `MultiStealthyPotential::SetConfiguration()` still owns the full copy and prepares the contact neighbor list (`apps/CCOptimization/MultiStealthyPotential.cpp:231–258`). In the indexed path, `UpdateSubconfigs()` binds views instead of rebuilding S `Configuration` objects. Preserve the old binding for other callers and for a fallback if metadata is invalid. Invalidate rho whenever positions or species membership change.

This is an evaluation-path speedup for FINUFFT and its direct fallback; it changes no transform formula. Confirm that local species order remains exactly `species_constraints[s].idx`, as the current builder promises (`apps/CCOptimization/MultiStealthyPotential.cpp:311–320`). Predicted total reduction is **0.1–0.3 ms** at either χ. It is ranked fourth because the measured configuration-and-set phase is only 0.45–0.5 ms, and the full phase cannot disappear.

## Shared plumbing and benchmark

Build the app with a default-off `USE_FINUFFT=1` toggle that supplies `-DCCPOTENTIAL_USE_FINUFFT`, the FINUFFT include path, library, and runtime path to **both** executable links in `apps/CCOptimization/makefile:41–55`. Keep the default build free of a FINUFFT dependency. In `GetMultiCCO()`, add an explicit `direct`/`finufft` backend choice after species creation, apply it to every `species_constraints[s].CCPotential`, and log requested and actual backend plus fallback reason. Keep CLI parsing compatible with the existing positional arguments and input stream (`apps/CCOptimization/main.cpp:1019–1044,1152–1164`). Direct remains the default.

Build one fixed-coordinate harness that records configuration/set, rho, CC energy, contact energy, and all-force times separately. Replay identical 1–3D orthogonal and skew cells, variable species sizes and χ, contact on/off, and both ground and MD call orders. Compare energy and **each force component** with relative \(10^{-10}\) or absolute \(10^{-10}\) near zero; also check finite differences and energies near \(10^{-14}\). Run separate-process same-backend repeats at 4 and 8 threads and compare endpoint files and pass records bitwise. Existing repeatability and Type 1 suites provide a starting oracle (`docs/finufft/RELEASE_VALIDATION.md:1–27`). Benchmark full optimizations from matched initial configurations, reporting callback counts alongside wall time: different valid evaluator rounding can change the L-BFGS trajectory.

## Combination plan

Implement and benchmark each branch from the shared-plumbing commit. **A+B+C+D can compose.** A and B both edit `ShiftedCCPotential` mode handling; merge their grid-map and plan ownership into one per-species cache with separate Type 1 and Type 2 plans. B and D both manage angle buffers; use one indexed gather. C must construct any new plans before concurrent execution if concurrent planning contends, then execute distinct species plans in parallel. Preserve direct fallback at the species boundary.

For the measured case, a combined target of roughly **1.5–2.0 ms at χₛ=0.1 (1.4–1.9×)** and **1.8–2.7 ms at χₛ=0.4 (3.4–5.2×)** is plausible if Type 2 accuracy passes and concurrent persistent-plan execution scales. These are planning ranges; 3D grid and \(w^3\) costs can reverse the crossover, so the implementation should retain direct selection per species.
